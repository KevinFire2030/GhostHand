# 개인 자동화 PoC를 사내 배포 가능한 AX 도구로 확장하기

## 문제 제기: 핵심 병목

사내 시스템은 대부분 SaaS 형태로 운영된다. 문제는 많은 SaaS가 업무 자동화에 필요한 API를 충분히 제공하지 않는다는 점이다.

API가 있으면 가장 좋다. 인증, 권한, 데이터 조회, 입력, 다운로드를 안정적인 방식으로 처리할 수 있기 때문이다. 하지만 현실에서는 API가 없거나, 있더라도 일부 기능만 제공하거나, 사내 업무에 필요한 화면 기능과 API 기능이 서로 맞지 않는 경우가 많다.

그렇다고 API가 제공될 때까지 마냥 기다릴 수는 없다. 반복 업무는 이미 매일 발생하고 있고, 사용자는 계속 브라우저를 열어 같은 메뉴를 누르고, 같은 조건을 입력하고, 같은 파일을 다운로드하고, 같은 형식으로 정리한다.

이때 여러 대안 중 하나가 **브라우징 자동화**다. 사람이 브라우저에서 수행하던 반복적인 작업을 자동화해서 수동 작업 시간을 줄이는 방식이다.

예를 들면 다음과 같은 업무가 있다.

- `myFinance`: 경비처리, 영수증 업로드, 항목 입력, 제출 전 확인
- `GSCM`: 물동 데이터 조회, 조건 입력, 엑셀 다운로드
- `M-Tracker`: Meta에서 제공하는 마켓 정보 조회, 데이터 다운로드, 엑셀 정리

이런 업무는 API가 없어도 브라우저 화면에서는 사람이 처리할 수 있다. 따라서 화면 조작을 안정적으로 자동화할 수 있다면, API가 없는 상태에서도 실질적인 AX 효과를 만들 수 있다.

## Codex 기반 PoC의 장점과 한계

앞선 실습에서 확인한 것처럼 `Codex + Chrome Extension + Chrome DevTools Recorder` 조합은 개인 업무 자동화 PoC를 만들기에 꽤 강력하다.

Chrome DevTools Recorder로 실제 사용자의 클릭, 입력, 페이지 이동을 녹화하고, Codex가 그 JSON export를 읽어 자동화 흐름을 이해한다. 이후 Chrome Extension을 통해 실제 로그인된 Chrome 세션에서 자동화를 재현할 수 있다.

이 방식의 장점은 분명하다.

- 업무 담당자가 실제 화면에서 수행한 흐름을 빠르게 수집할 수 있다.
- Codex가 selector, URL, 입력 필드, 성공 기준을 이해하는 데 도움이 된다.
- Playwright/Puppeteer 기반 자동화 로직으로 전환하기 쉽다.
- 로그인된 브라우저 상태를 이용할 수 있어 SSO나 2FA 이후 작업을 검증하기 좋다.
- 개인 PoC나 스킬 형태로 만들면 빠르게 반복 실험할 수 있다.

하지만 한 가지 큰 문제가 있다.

**혼자 쓰기에는 좋지만, 다른 사람에게 쉽게 배포하기 어렵다.**

특히 다음 사용자에게는 Codex 기반 자동화를 그대로 쓰게 하기 어렵다.

- Codex를 사용할 수 없는 외주 용역 직원
- 행정 사원
- 개발 도구에 익숙하지 않은 일반 업무 담당자
- 보안 정책상 AI 도구 접근이 제한된 사용자
- 반복 업무는 많지만 자동화 스크립트를 직접 다룰 수 없는 사용자

즉, Codex 기반 PoC는 자동화 흐름을 발굴하고 검증하는 데는 좋지만, 최종 사용자 배포 도구로는 별도의 포장이 필요하다.

## 해결 방향

핵심 방향은 다음과 같다.

> Codex로 자동화 흐름을 빠르게 발굴하고 검증한 뒤, 배포용 런타임은 따로 만든다.

즉, Codex는 개발자나 자동화 담당자가 쓰는 **업무 흐름 분석 및 검증 도구**로 사용한다. 실제 사용자에게는 Codex가 아니라 별도의 앱이나 실행 도구를 제공한다.

추천 구조는 다음과 같다.

```text
1. Codex + Recorder로 업무 흐름 분석
2. Playwright/Puppeteer 스크립트로 자동화 로직 정리
3. Electron 앱 또는 사내 웹앱 형태로 포장
4. 사용자는 버튼만 누름
5. 자동화는 사용자 브라우저 세션 또는 사내 인증 환경에서 실행
6. 로그, 실패 지점, 재시도, 수동 개입 지점 제공
```

이 구조에서는 최종 사용자가 Codex를 몰라도 된다. 사용자는 업무 자동화 앱에서 버튼을 누르고, 앱이 내부적으로 브라우저 자동화를 수행한다.

## 업무별 적용 예시

### myFinance 경비처리 자동화

경비처리는 API가 없더라도 브라우징 자동화의 효용이 큰 대표 업무다.

가능한 흐름은 다음과 같다.

```text
1. 사용자가 영수증 파일을 선택한다.
2. 앱이 영수증 정보를 추출하거나 사용자가 항목을 확인한다.
3. myFinance를 연다.
4. 필요한 메뉴로 이동한다.
5. 경비 항목, 금액, 날짜, 가맹점 정보를 자동 입력한다.
6. 제출 직전 화면에서 멈춘다.
7. 사용자가 최종 확인 후 직접 제출한다.
```

여기서 중요한 점은 자동화가 모든 것을 끝까지 처리하지 않는다는 것이다. 경비 제출은 회계와 감사 이슈가 있으므로, **제출 직전에서 멈추고 사용자가 최종 확인**하는 구조가 안전하다.

### GSCM 물동 데이터 다운로드

GSCM처럼 주기적으로 데이터를 조회하고 엑셀을 다운로드하는 업무는 자동화 효과가 크다.

가능한 흐름은 다음과 같다.

```text
1. 사용자가 조회 기간이나 조건을 입력한다.
2. 앱이 GSCM에 접속한다.
3. 정해진 메뉴로 이동한다.
4. 기간, 조직, 물류 조건 등을 입력한다.
5. 조회 버튼을 누른다.
6. 엑셀 다운로드를 실행한다.
7. 지정 폴더에 저장한다.
8. 파일명을 표준 규칙에 맞게 변경한다.
```

이 유형은 결제나 제출 같은 위험 액션이 적고, 결과물이 파일로 남기 때문에 브라우징 자동화의 초기 적용 대상으로 적합하다.

### M-Tracker 마켓 정보 수집

M-Tracker처럼 외부 플랫폼 또는 파트너 SaaS에서 정보를 조회하고 다운로드하는 업무도 자동화 후보가 될 수 있다.

가능한 흐름은 다음과 같다.

```text
1. 사용자가 수집 조건을 선택한다.
2. 앱이 M-Tracker 또는 Meta 관련 화면에 접속한다.
3. 기간, 국가, 카테고리, 브랜드 등 조회 조건을 입력한다.
4. 데이터를 다운로드한다.
5. 여러 파일을 병합하거나 표준 엑셀 형식으로 정리한다.
6. 결과 파일을 지정 폴더에 저장한다.
```

이 업무는 단순 다운로드뿐 아니라 후처리까지 묶으면 효용이 더 커진다. 브라우저 자동화와 엑셀 자동화를 함께 구성하면 사용자는 결과 파일만 확인하면 된다.

## 배포 방식 후보

브라우징 자동화를 다른 사람에게 배포하려면 실행 환경을 어떻게 제공할지가 중요하다. 현실적인 후보는 세 가지다.

## 1. Electron 데스크톱 앱

가장 현실적인 1차 배포 방식은 Electron 데스크톱 앱이다.

Electron 앱은 쉽게 말하면 **웹 기술로 만든 데스크톱 프로그램**이다. HTML, CSS, JavaScript, React 같은 웹 기술로 화면을 만들고, 사용자는 일반 Windows 프로그램처럼 실행한다.

감각적으로는 Android 네이티브 앱의 WebView와 비슷하다. 다만 Electron은 단순 WebView보다 더 많은 일을 할 수 있다.

```text
Android WebView 앱
= 네이티브 앱 껍데기
+ Android WebView

Electron 앱
= 데스크톱 앱 껍데기
+ Chromium
+ Node.js
```

Electron 앱은 웹 UI를 제공하면서도 로컬 PC 자원에 접근할 수 있다.

- 파일 읽기/저장
- 엑셀 다운로드 파일 정리
- 로컬 설정 저장
- 백그라운드 작업 실행
- Playwright/Puppeteer 자동화 실행
- 실패 시 스크린샷 저장
- 실행 로그 저장

사내 업무 자동화 앱으로 만들면 사용자는 다음과 같은 화면을 보게 된다.

```text
[myFinance 경비처리 자동화 실행]
[GSCM 물동 데이터 다운로드]
[M-Tracker 마켓정보 수집]
```

사용자는 버튼만 누른다. 앱은 내부에서 브라우저를 열거나 연결하고, 필요한 자동화 흐름을 실행한다.

Electron 방식의 장점은 다음과 같다.

- 외주/행정 직원에게 설치 파일로 배포할 수 있다.
- UI를 업무 담당자 친화적으로 만들 수 있다.
- Playwright/Puppeteer를 내장하기 쉽다.
- 다운로드 파일, 엑셀 후처리, 로그 저장 같은 로컬 작업을 처리하기 좋다.
- PoC 이후 사내 배포용으로 전환하기 가장 무난하다.

단점도 있다.

- 설치와 업데이트 체계가 필요하다.
- 보안 정책상 로컬 자동화 앱 배포 승인이 필요할 수 있다.
- 각 사용자 PC의 브라우저, 권한, 네트워크 환경 차이를 고려해야 한다.
- SaaS UI가 바뀌면 앱 업데이트가 필요하다.

## 2. Chrome Extension

두 번째 후보는 Chrome Extension이다.

사용자가 실제 SaaS 화면을 보고 있을 때, 그 위에 자동화 버튼이나 패널을 제공할 수 있다.

예를 들면 다음과 같은 UX가 가능하다.

```text
현재 GSCM 화면에서:
[이번 달 물동 데이터 다운로드]

현재 myFinance 화면에서:
[영수증 정보 자동 입력]

현재 M-Tracker 화면에서:
[현재 조건으로 데이터 수집]
```

Chrome Extension의 장점은 다음과 같다.

- 사용자가 보고 있는 페이지 위에서 바로 동작할 수 있다.
- "이 화면에서 데이터 추출", "이 폼에 자동 입력" 같은 UX가 좋다.
- 로그인된 사용자의 현재 브라우저 세션을 자연스럽게 활용할 수 있다.

단점은 다음과 같다.

- 여러 SaaS를 한 확장으로 통합할수록 권한 관리가 복잡해진다.
- 파일 다운로드, 엑셀 후처리, 로컬 저장소 관리에는 Electron보다 제약이 있다.
- 사내 배포와 업데이트 정책을 별도로 마련해야 한다.
- 페이지별 DOM 변화에 민감하다.

Chrome Extension은 특정 SaaS 화면에서 가벼운 보조 기능을 제공할 때 잘 맞는다. 여러 업무를 묶은 통합 실행 도구로는 Electron이 더 편할 수 있다.

## 3. 사내 웹 포털 + 로컬 에이전트

장기적으로 가장 제품화에 가까운 방식은 사내 웹 포털과 로컬 에이전트를 결합하는 구조다.

사용자는 사내 웹 포털에 접속해 자동화 업무를 선택한다. 실제 브라우저 조작은 사용자 PC에 설치된 로컬 에이전트가 수행한다.

```text
사내 웹 포털
- 업무 목록 제공
- 실행 파라미터 입력
- workflow 버전 관리
- 실행 이력 확인
- 권한 관리

로컬 에이전트
- 사용자 PC에서 브라우저 자동화 실행
- 다운로드 파일 저장
- 스크린샷/로그 수집
- 수동 개입 지점 처리
```

이 방식의 장점은 다음과 같다.

- 중앙에서 workflow 버전을 관리할 수 있다.
- 사용자별 권한과 실행 이력을 관리하기 좋다.
- 여러 업무 자동화를 하나의 플랫폼처럼 확장할 수 있다.
- 장기적으로 운영, 모니터링, 감사 로그를 붙이기 좋다.

단점은 초기 구현 비용이 높다는 점이다. 처음부터 이 구조로 가면 PoC 속도가 느려질 수 있다.

## 추천 로드맵

처음부터 거창한 플랫폼을 만들기보다, 작은 업무부터 검증하고 점진적으로 확장하는 편이 현실적이다.

추천 순서는 다음과 같다.

```text
1단계: Codex + Recorder로 업무 자동화 PoC 제작
2단계: 반복 가치 높은 업무 1~2개를 Playwright 스크립트로 고정
3단계: Electron 앱으로 포장
4단계: 사용자 입력값, 실행 로그, 실패 캡처 추가
5단계: 여러 업무를 플러그인/스킬처럼 추가
6단계: 사내 포털 또는 중앙 관리형 에이전트로 확장
```

핵심은 **AI를 최종 사용자에게 직접 쓰게 하는 것**이 아니다.

더 현실적인 방향은 다음과 같다.

```text
AI와 Codex:
자동화 흐름 발굴, PoC 제작, selector 보정, 유지보수 지원

최종 사용자:
버튼형 업무 자동화 도구 사용
```

즉, AI는 자동화 개발과 유지보수의 생산성을 높이고, 최종 사용자는 복잡한 도구를 몰라도 되게 만드는 구조다.

## 안전 설계 원칙

브라우징 자동화는 편하지만, 사람의 브라우저를 대신 조작한다는 점에서 안전 설계가 중요하다.

다음 액션은 자동화가 직접 끝까지 실행하지 않는 것이 좋다.

- 구매
- 결제
- 실제 제출
- 회원정보 변경
- 비밀번호 입력
- 개인정보 조회 범위 확대
- 삭제 또는 취소 처리

특히 경비처리, 정산, 결제, 개인정보 변경처럼 책임이 따르는 업무는 **최종 확인 단계에서 멈추는 구조**가 필요하다.

권장 패턴은 다음과 같다.

```text
자동화가 초안 작성
-> 자동화가 제출 직전 화면에서 멈춤
-> 사용자에게 요약 표시
-> 사용자가 직접 확인
-> 사용자가 최종 제출
```

또한 운영 단계에서는 다음 기능이 필요하다.

- 실행 로그 저장
- 실패 시 스크린샷 저장
- 어느 단계에서 실패했는지 표시
- 사용자가 이어서 수동 처리할 수 있는 중단점 제공
- SaaS UI 변경 시 selector 업데이트 체계 마련
- 민감정보를 로그에 남기지 않는 정책

## 정리

API가 없는 SaaS 업무를 자동화하기 어렵다는 문제는 현실적인 병목이다. 하지만 API가 제공될 때까지 기다리기만 하면 반복 업무의 비효율은 계속 누적된다.

브라우징 자동화는 이 공백을 메우는 실용적인 대안이 될 수 있다.

다만 `Codex + Chrome Extension + Recorder` 조합을 최종 사용자에게 그대로 배포하는 방식은 적합하지 않다. 이 조합은 자동화 흐름을 발굴하고 검증하는 데 사용하고, 실제 배포는 Electron 앱, Chrome Extension, 사내 웹 포털 + 로컬 에이전트 같은 형태로 분리하는 것이 좋다.

현실적인 첫걸음은 다음과 같다.

```text
Codex + Recorder로 PoC를 빠르게 만든다.
반복 가치가 높은 업무를 Playwright/Puppeteer 로직으로 고정한다.
Electron 앱으로 포장해 비개발자도 버튼으로 실행하게 한다.
실행 로그, 실패 캡처, 수동 확인 지점을 붙인다.
검증된 업무를 하나씩 확장한다.
```

이렇게 접근하면 API가 없는 SaaS 환경에서도 사내 업무 AX를 현실적으로 시작할 수 있다.
